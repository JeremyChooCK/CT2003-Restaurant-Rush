1. Overview and how to run

Restaurant Rush is a turn-based game in which the player manages a small restaurant for 18 turns. Each turn the player decides what the Host (Stage 3), Waiter and Chef do. The Cashier works automatically. Customers choose their own food and lose patience while they wait. After turn 18 the player wins only if at least 4 customers paid, revenue is at least $45.00 and the average satisfaction of paid customers is at least 60.

The game needs only JDK 17 or newer and works fully offline. Build with build.bat or ./build.sh, play with run.bat or ./run.sh, and run the 40 automated rule checks with test.bat or ./test.sh. Every recorded run in this report can be replayed exactly, for example java -cp out restaurantrush.Main --echo < runs/stage3-victory.txt.

The code follows the Boundary-Control-Entity structure. boundary only reads input and prints the state. control holds the turn loop and all game rules. entity holds the restaurant's objects and keeps them consistent. No rule lives in the user interface.

3. Design discussion

3.1 Key abstractions and their responsibilities

ClassKindResponsibility
GamecontrolApplies the turn rules: arrivals, staff actions, eating and payment, satisfaction loss and departures, Happy Hour timing. Turns the player's numeric choices into objects and reports what happened as event messages. No input or output.
GameControllercontrolRuns the 18-turn loop in the brief's order. Asks the view and input for each decision and retries when Game rejects a choice.
ScenariocontrolAll setup in one place: turns, tables, menu, arrival schedule and seed. Later stages register new customers and menu items here.
PriceCalculator, PriceModifier, HappyHourcontrolLocks an order's price: customer discount first, then each restaurant-wide modifier. HappyHour is one modifier and also manages its two-turn duration and the +15 recovery.
GameStats, ObjectivecontrolRunning totals (revenue only from paid bills) and the victory check.
RestaurantentityOwns the tables, the waiting queue, customers and orders, and keeps them consistent when customers are seated, pay or leave.
Customer + subclassesentityThe visit state machine and satisfaction. Subclasses supply patience, discount, food choice and reaction to service.
OrderentityLocked price, preparation progress and status.
MenuItem, Dish, ComboMeal, MenuentityWhat can be ordered, its price and its preparation units.
Staff + Waiter, Chef, Cashier, HostentityEach enforces "at most one task per turn" and validates its own actions.
MoneyentityImmutable amount in integer cents with half-up rounding.
ConsoleView, ConsoleInputboundaryDisplay the state, and read and format-check numbers and yes/no answers.

3.2 Object-oriented concepts in the code

Encapsulation. Customer, Order and Table expose read-only getters. Their state changes (seatAt, placeOrder, serve, pay, leave, prepareOneUnit) are package-private, so only the restaurant and its staff can move a customer through the visit, and the UI cannot. Satisfaction can only change through loseSatisfaction(), recover() and the protected changeSatisfaction(), which keep it between 0 and 100. Money is immutable and hides its cents, so a locked price cannot be altered later. Staff hides the "already acted" flag behind ensureAvailable() and completeTask().

// Staff subclasses validate first and only then use up the task (Waiter.seat)
public void seat(Restaurant restaurant, Customer customer, Table table) throws InvalidActionException {
    ensureAvailable();                 // throws if the Waiter already acted this turn
    restaurant.seat(customer, table);  // throws if the customer is not queued or the table is taken
    completeTask();                    // reached only when the action succeeded
}

Inheritance. RegularCustomer, VIPCustomer and CriticCustomer extend Customer. Dish and ComboMeal extend MenuItem. Waiter, Chef, Cashier and Host extend Staff, sharing the one-task-per-turn mechanism.

Polymorphism. The rules never check a customer's type. Game calls customer.loseSatisfaction(), which uses the subclass's getSatisfactionLoss(). PriceCalculator calls applyDiscount(). Waiter.serve() triggers onServed(), which only the Critic overrides. Game asks for chooseItem(menu), which the Critic overrides to pick the most expensive item. Similarly, the Chef and Order only call getPrepUnits() and getPrice() on a MenuItem, whether it is a dish or a combo.

// Game.processSatisfactionAndDepartures(): one loop for every customer type
for (Customer customer : restaurant.getActiveCustomers()) {
    if (!customer.isAwaitingService()) { continue; }
    customer.loseSatisfaction();               // 8, 5 or 12 depending on the object
    if (customer.getSatisfaction() == 0) { restaurant.handleDeparture(customer); ... }
}

Composition and aggregation. Restaurant creates and owns its Tables (composition). Game owns its staff, statistics, objective, price calculator and Happy Hour. ComboMeal is built from two existing MenuItems (aggregation: the dishes also exist on their own). It is itself a MenuItem, a small Composite pattern, which is why combos needed no change to Order or Chef.

3.3 SOLID principles (only where they are really in the code)

PrincipleWhere it appears
Single responsibilityConsoleInput only parses input, ConsoleView only formats output, GameController only sequences the turn and retries, Game only applies rules, GameStats/Objective only score, and PriceCalculator only prices. For example, changing the victory targets touches Objective alone.
Open/closedStage 2 added two customer types without modifying Customer, Game's rules, Waiter or Cashier; only the Scenario setup changed. Stage 3 added combos without modifying Order, Chef or Menu, and Happy Hour pricing plugs into PriceCalculator as a PriceModifier. A future promotion would be one new class.
Liskov substitutionAny Customer subclass works wherever a Customer is expected. They keep the contract: loss is positive, a discount never raises a price, and satisfaction stays 0–100 because only the base class changes it. A ComboMeal can be ordered, cooked and priced exactly like a Dish. Host keeps Staff's one-task rule.
Interface segregationOnly lightly reflected. PriceModifier is a single-method interface, so HappyHour implements only what pricing needs. We did not add interfaces where there was only one implementation.
Dependency inversionPriceCalculator depends on the PriceModifier abstraction, not on HappyHour. Rules depend on the abstract Customer, MenuItem and Staff. (GameController still uses the concrete console classes; see trade-offs.)

3.4 Coupling and cohesion

Dependencies point one way: boundary → control → entity. The entity package does not import anything from control or boundary, so it compiles on its own. Classes are cohesive: each entity looks after its own state, and each control class has one job. The main coupling hotspot is Game, which coordinates many entities. We accepted this because it is the single place that knows the turn order. It acts as a façade, so the controller and view only talk to Game and read entity getters.

4. Trade-offs and an alternative design

DecisionBenefitCost
Package-private state changes in the entity packageStrong encapsulation: only staff and the restaurant can change a customer's state.All entity classes must live in one package.
Extension hooks in Customer from Stage 1 (applyDiscount, chooseItem, onServed)Stage 2 needed no change to Customer or the rules.Stage 1 contains two hooks that Regular customers do not override.
Game returns event messages as stringsSimple, and the view just prints them.Game holds English text; a GUI would prefer event objects.
Happy Hour wired into Game and GameController directlySimple and easy to follow.Stage 3 had to modify those two classes. A generic "turn listener" mechanism would avoid that but was more than this game needs.
Each customer has its own seeded random sequenceChoices are reproducible, even if the player makes and corrects mistakes.Food choice is not influenced by game state.
Concrete console classes in GameControllerLess code and no unnecessary interfaces.A GUI would need a small view interface to be extracted.

Alternative considered: a CustomerType enum with switch statements. A single Customer class with a type field, where Game and PriceCalculator switch on the type to decide the loss, discount and special behaviour. It is shorter for three types, but every new type would require editing the turn rules in several places and testing them again. That breaks the open/closed principle and the brief's requirement that behaviour be dispatched through the customer objects. We chose subclasses, so Stage 2 only added two files.

We also considered the Command pattern for staff actions (one class per action). It would allow undo and logging, but the game has only a few actions and needs no undo, so plain methods on Game were clearer.

5. How the player's choices change the result

Every customer gets the same 18 turns, but the staff are the bottleneck. With one Waiter and an arrival every three turns, seating, taking the order and serving already fill the Waiter's turns. Any delay costs satisfaction, and a late customer may not pay before turn 18.

  • Order of tasks. In Stage 1, seating each customer on arrival, taking the order next turn while the Chef cooks it, and serving the turn after gives five paid customers at 84 satisfaction each (victory, $57.00). A manager who stops after the first customer ends with one payment and a walk-out (defeat).
  • Critic timing (Stage 2). The Critic rewards a dish served on the earliest possible turn (+10) and punishes any delay (−10). In the Stage 2 victory, on turn 13 the Waiter serves the Critic on time (64 → 74) and lets the newly arrived C5 wait one turn. In the defeat run the Critic, losing 12 per turn, walks out.
  • Happy Hour versus serving (Stage 3). On turn 13 the Critic's 3-unit combo is ready just as C5 arrives with a 3-unit combo. Serving the Critic first would leave C5 unable to pay before turn 18. The player switches on Happy Hour, lets the Host seat C5, takes C5's order at 20% off and serves the Critic one turn late. The +15 recovery on turns 13 and 14 outweighs the Critic's −10 (recorded satisfaction 72), and all five customers pay: victory with $92.58 and an average of 86.0. Wasting Happy Hour on turn 1 and neglecting the kitchen leads to defeat with no payments.
  • Revenue against satisfaction. Happy Hour cuts prices by 20%, so using it on expensive orders lowers revenue. Its value is keeping waiting customers above the walk-out line.

8. Additional features

  • Reproducible scripted play. Any text file can be redirected into the game. Lines starting with # are comments, and when a script ends every remaining choice safely defaults to "Wait". --echo prints each answer so transcripts read like a live session. This makes the victory and defeat demonstrations repeatable.
  • Configurable seed (--seed N) to try different customer orders. The default 2003 is used for all evidence.
  • Offline rule checks (40 checks, no test library), including a turn-by-turn replay of the brief's Section 3.3 example and the brief's price examples ($24.30 combo, $10.80 VIP Happy Hour burger).
  • Helpful display: each turn lists the useful task for every staff member, the turns left in Happy Hour, and the menu price whenever a discount applies.
  • Pixel-art window (run.bat --gui): an animated graphical version of the same game, added after stage-3. It is a second boundary: PixelGame calls the same public Game actions as the console and PixelRoom only draws the current state, so no rule was changed or duplicated. Its shift log also shows each waiting customer's satisfaction loss and whether each served order was discounted.
  • Demo jumps in the pixel-art window: DemoJump starts a fresh game and replays the recorded victory or defeat run to a chosen point (turn 4 VIP, turn 10 Critic, turn 13 Happy Hour decision, or either ending), so a presenter can move forwards or back and always reach the same state.

9. Reflection

What went well. Planning the customer and menu hierarchies before Stage 1 paid off. Stage 2 needed two new classes and a two-line setup change, and combos in Stage 3 needed no change to orders or the kitchen. Writing the rule checks early, starting with the brief's Pasta example, caught timing mistakes. Examples were "served this turn" versus "next turn" and when a customer becomes ready to pay.

What was harder than expected. The order of events within a turn (Host, then Waiter, then Chef, then payment, then satisfaction loss) has many edge cases. One example: whether Happy Hour recovery happens before or after the new arrival. Making every invalid choice "free" required a strict validate-first, act-second pattern in every staff class.

What we would do differently. We would introduce Happy Hour through a general turn-event mechanism, so that Stage 3 changed Game and GameController less. We would also return event objects instead of text. The pixel-art window did reuse Game unchanged, but it can only print the English messages from Game; with event objects it could react to each event directly.

What we learned. Good object-oriented design shows up when requirements change. The stage tags let us measure this directly by how few existing lines each new stage had to touch.
